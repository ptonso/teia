# 2026-09-24

## Goal

Teach a fresh agent to work with Teia in a new project, driven by the CLI instead of exploring the repository. The auto-research lab skills are archived (`packages/teia/deprecated/`) for later ideas. Research automation is a later stage, built on top of this skill.

## User preferences

- Symlinks are the wiring mechanism: one source of truth, works from a pip install because `teia init` links into the installed package.
- The skill follows the CLI to learn what exists and what does not. It covers wiring configs, what configs mean, minimal swaps, new config files and new custom components.
- One skill for now. Replace `core-config`.

## Decisions

- Output kind: code (configs, commands, Python). Shape: router plus one guide per rung of an escalation ladder (override, select, new config, new component), because each rung needs different steps and verification.
- Specs are not shipped in the wheel, so the skill never links to them. Contracts are taught as a search: read the installed `teia.base.*` sources and a working neighbour found through `config show`.
- Kept the model in brief to the few facts a cold agent needs to read CLI output (three graphs, envelope, `# @package` address, pipeline as bundle, layers). Everything the CLI reports (groups, options, pipelines) stays out of the skill.
- Ground rule about same-path project files being ignored: found by testing an overlay. Teia's intent is project-first (a test asserts it), but Hydra's actual order puts the project last. Deferred in the specs log; the skill teaches new names.

## Known limits

- No CLI command lists Python component contracts. Discovery of contracts goes through reading source. A component-inspection command is a candidate follow-up.
- `teia config show` reports a project file as winning when the same path exists in a packaged layer, though Hydra ignores it.

## Cold test (subagent, scratch project, CLI only)

Both tasks (swap an encoder in a tabular pipeline, add a custom loss) succeeded. Gaps found and how they were generalized:

- A plain group selection merges into the node a pipeline already fills, leaving stale keys; the `group@netmodule.<key>` form replaces it. The skill now teaches the difference, how to read it from `config explain`, and to read the changed node in full. `config explain` crashed on the `@` form; fixed in the CLI (slot-qualified selections are dropped from the recompositions and attributed to `CLI`).
- `config init` stubs carry placeholder targets and cannot be limited to one file: the skill says to keep only the ones filled in.
- Loss and forward arguments arrive in `in` order, and project-root modules need no `__init__.py`: added to `write-component.md`.
- The opening said not to read Teia's source, while the CLI itself prints package paths and the component guide sends the agent to installed source: reworded to "open the file a CLI answer points at".
- `logs/` sits inside the linked skill folder as noise for the agent. Kept beside `SKILL.md` per the create-skills convention; revisit if it confuses runs.

## Task-contracts rewrite

The config layer moved from pipelines and bundles to tasks (a contract class plus per-task module folders) and `node/{data,net,eval}` leaves. The skill was rewritten to match, keeping its shape: router plus one guide per rung.

- The model in brief now teaches the three graphs, leaf vs module, and the task as a contract over two seams. Pipelines and `# @package` addresses are gone from it.
- The escalation ladder gained a rung, "swap to another module in the task's folder", because folder membership now means "valid swap" (a conformance test enforces it). `teia config tree --root netmodule/<task>` answers "which architectures fit".
- The activation contract (flat atoms from an inline `kernel`, `capture:` map) is taught by pointing at the `BaseActivation` docstrings, which state it; the skill only says where atoms go.
- `teia config init --from task=<t>` is the full-control scaffold: resolved modules under `mine/`, keeping the contract check with `task=`.

Audit against create-skills after the rewrite: every command and flag named by the skill was run against the CLI in a scratch project, including the same-path overlay rule (still ignored, `config list` still prints the project layer second). Fixed wording drift ("writes the report" became "runs the evalmodule"), added eval-side node kinds to `write-component.md`, and updated stale CLI help strings (`explain`, `--skip-report`).

## Second rewrite: teach the idea and the questions, not the catalogue

User feedback on the first task-contracts version: the language read as robotic and cold, and it hardcoded component names and config paths that change with every release.

Preferences stated:

- Why the skill names no components or paths: Teia grows quickly, so anything listed goes stale. That is the reason for the design, and it stays in this log. The skill itself only teaches the behavior (ask the CLI, read the installed code) and never mentions its own upkeep.
- The skill teaches an agent, in one read, how Teia is organised (the three graphs, the two seams, node leaves vs modules vs tasks, and why the contract makes swapping safe) and how to ask the CLI for everything else. It names no tasks, components or file lists, so it does not need an update per release.
- It supports three levels of work: (1) take a task's defaults, (2) swap components from the task's folders, (3) write new config and Python components that respect the base classes and templates.
- Situations it must handle without further prompting: prepare a user's data for a train, wire the CLI for experiments, audit whether a component exists, and create a missing component in the right folder (for nn nodes, the fan by assumes placement) and wire it into config.
- Text should be pedagogical: explain why, address the reader as a colleague.

Decisions:

- `discover.md` became `inspect.md`, gaining a "does it already exist" audit (purpose, contract, text, near miss) that gates level 3. Level 1 got its own guide, `use-a-task.md`, because getting data into the reader's layout is most of the work there. The reader's module docstring is the source of truth for the layout, reached through `config show` and the `_target_`.
- Placement is taught as a procedure that ends at the shipped folder READMEs (the nn tree's placement ladder), not as a copy of the ladder. For a project, the component goes in the project's own package under a mirror of the library's relative path, so it can graduate by copying.
- Contract and activation details are left to the base-class docstrings and to a neighbouring component as template.

Facts corrected while verifying commands against the CLI:

- `teia train ... -c job` prints the composed config but does not check the task contract or run any node. The first version said pre-flight ran under it. The contract check happens in a real run's pre-flight, so `++trainer.fast_dev_run=true` is the cheap way to see contract errors. The skill now teaches three layers: lint, `-c job`, fast dev run.
- A project-defined task contract could not be imported, because the project directory joined `sys.path` after pre-flight. Fixed in the engine (both entry points) with a regression test. The skill can now teach "a new task" as contract class plus modules plus preset.
- A project task preset must start with `# @package _global_`. `teia config show` strips that header, so a copy of its output needs the line added back. Lint reports it.

Not yet done: a cold run by a subagent on the rewritten skill, as the first session did. Known noise: about 25 shipped README and docstring lines in the component library point at a spec file that no longer exists, which agents may follow from the placement READMEs.
