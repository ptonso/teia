# 2026-10-09

Plugin model added to the skill, after a long design session on how teia, private and public plugins, research projects and baselines relate.

- The user's model: every research project is a teia plugin, the single source of truth for its contribution. Other projects reuse it by installing it, never by copying it. Code that does not speak teia is wrapped once. Teia is one package with a stable language (base, core), frozen-once-released task contracts, and a growing zoo.
- Ownership is visible in names: the plugin's own Python package, and an owner folder named after the package in every config path (`netmodule=<task>/<package>/<name>`). The user agreed to mirroring teia's layout; the owner folder was my recommendation and is enforced by `teia plugin check`.
- Baselines: three ways (trained, frozen, imported), cheapest that keeps equal what the claim is about. Verified in a sandbox that a frozen baseline works today: a netmodule with no loss node runs with `epochs=0` (fit skipped, test and eval still run). There is no importer for saved predictions; the guide says so instead of inventing one.
- Licenses: copyleft code never enters teia; it lives in a wrapper plugin with the same license. The user chose Apache-2.0 for teia.
- New guides make-a-plugin, baselines, publish. inspect, write-config and write-component now place files in `src/<package>/` with owner folders; the old advice (a package in the project root resolving without install) is gone, since a plugin is installed editable.
- `teia plugin init` was added so the agent scaffolds deterministically instead of hand-writing pyproject and the search-path file.
- Skills of installed plugins are now linked by `teia init`, so a plugin can ship its own skill to the projects that install it.

## Agent test, same day

Three Sonnet agents ran the skills cold in isolated sandboxes: make a plain project a plugin, add a frozen scikit-learn baseline, publish a project that borrowed an encoder from a private plugin. All three succeeded; the runs exposed:

- A frozen model with no trainable parameter crashed in optimizer construction under `epochs=0`; the agent worked around it with a placeholder parameter. Fixed in the engine (no optimizer when nothing trains; an error if epochs > 0), and the guide now says so.
- An agent named its preset after the dataset (`digits.yaml`). The layout already said `<task>.yaml`; the move step now says it explicitly, and the checker has a `task-name` rule.
- An agent reported the dataset held two classes, from a partial listing; it held ten. The report rule now asks for how each claim about data or results was checked.
- An agent skipped `Upstream` for the user's own saved model, which is right; the guide now separates the user's artifacts from upstream code.
- Setting up the publish scenario showed the `provider` rule missed leaves mounted from another package; it now reads composed configs.

## Paper-sourced components, later the same day

First drafted as a separate guide (`implement-a-paper.md`, then `sourced-component.md`). The user rejected the name and found it too long with examples overfitted to graphs. Most of it applied to every component, so the general guidelines moved into write-component step 4, with the paper-specific part as its "From a paper" subsection; the docstring contract stays owned by teia `specs/docstrings.md`.

- Trigger: the teia-arsenal `GraphTransformer` (Graphormer). The user found it cluttered: everything compressed into a few dense lines, no `Args:`, and the paper's generality lost. Graphormer's preliminaries define AGGREGATE and COMBINE so that GCN, GIN and GraphSAGE are instances, and the code hardwired one of each with no name. The edge bias was spatial encoding cut to one hop, and centrality encoding was absent.
- The user's model of a good component: the CNN VAE encoder, neck and decoder in teia-arsenal. Generic without overhead, with useful config entries so one class specialises into other architectures. The guide cites them as the exemplar to study.
- Principles the user asked for: follow the article's notation, document the docstrings well, space the code so the important parts of the implementation stand out, expose the paper's abstractions as configuration.
- Placed as a guide inside the teia skill instead of a separate skill, since the skill's description already covers writing Python components and two skills would compete for the same requests.
- Generality rule I proposed and the user accepted: a slot becomes configurable when the paper itself treats it as one (defines it, ablates it, or reduces an earlier method to it). Omitted paper parts go under `Adaptations` instead of becoming disabled flags.
- Folding a neighbour into a preset (GATv2 as one AGGREGATE of the graph encoder) was raised. The guide makes it a proposal to the user, since it removes a component.
- First trial of step 4: the arsenal graph encoders became one `GraphEncoder` (Graphormer, GATv2, GraphSAGE, GIN as leaves). The user then asked for more room in docstrings, a module description that explains the idea instead of listing papers, a split of the large module (now node + `_aggregate.py` + `_combine.py`), and one leaf per purpose folder a component fills. Asked whether "one config per general class" meant config groups per AGGREGATE/COMBINE step; the user meant purpose folders.
- The user wants no invisible node modules (leading `_`): building blocks split out of a node live in public modules named for their role, listed in the folder README.
- Then the docstrings were too long: they now hold a summary line and the formula, without prose restating it.
- The main forward needed step comments: each paragraph now opens with a short comment naming its step and formula.
- Trailing comments on consecutive lines align in one column (asked by the user).

## `--dry-run`, later the same day

- The user wanted the `++` syntax out of the skills. Every guide used `++trainer.fast_dev_run=true` for the pre-flight because the default trainer group had no such key.
- Shipped in teia: `fast_dev_run: false` in `trainer/default.yaml`, and `teia train --dry-run`, which appends `trainer.fast_dev_run=true` to the overrides. The override is saved in `overrides.yaml`, so the post-train test and eval replay it. Checked on the iris task: fit, validate, test and eval each run one batch.
- Guides now say `--dry-run`. `write-config` has an "Avoid `++`" section: put the key in a leaf, module or preset, and give a run-time switch a real key and a flag.
